Intraday-engine and log-only rows have no `sr_daily` (another engine / no trades file): they count in N, not in V. Back-filled `config_hash` = SHA-256 of `"<source>\n<description>"` (unique per row, checked by the script: each row is one configuration); `date` = the file's modification date (FULL_DAILY_RUN.md rows: the document's date).
  - Ruling R36 (review, fix round 1): N = the number of distinct `config_hash` values in `TRIALS.csv` incl. the current run; V = sample variance over one `sr_daily` per hash (the latest row of the hash with one). Re-running an identical configuration adds a row but does not change N. The hash covers everything that changes the run (config fields except `final_holdout`, the pairs actually run, the pairs file's content, the closes name, whether volumes were used) and not the code revision. The first round counted rows (literal "N = rows"), and its back-fill hash ("backfill\n<source>") gave 16 trials 3 hashes; both fixed together. The almgren run's N includes the flat configuration; debugging used synthetic runs with the registry redirected.
  - Ruling R37: legacy runs are registered (conservative N) with `sr_daily` empty and a `LEGACY` description, and are not deflated.
  - `--final-holdout` runs: recorded in `HOLDOUT_USES.md` before the run (a failed run still counts as a use); one that reaches the holdout is not a development trial (no `TRIALS.csv` row), its DSR uses the registry + itself; one that ends before 2024 is both. Never run on real data.
  - γ = `np.euler_gamma` (0.5772156649…; the plan's "0.5772" rounded); population skewness / raw kurtosis (scipy defaults); SR̂ with the sample std (ddof = 1, as `mtm_stats`).
  - The guard uses the brief's last date min(cfg.end or the panel's end, the panel's end). No panel cut at cfg.end is added: T1's committed test (the run on the full panel equals the run on the panel cut at cfg.end) and the new boundary test show that no data after cfg.end is read (the fill-only bar is capped at cfg.end, R15).
  - `step4c_bootstrap_sharpe.py` is not pointed to `perf_stats.psr`: its `probabilistic_sharpe` feeds the **annualised** `sharpe()` (× √252) into the per-period formula, on equity `pct_change` returns of an intraday `trades.csv`, and returns 0.5 / 1.0 / 0.0 at edge cases — not trivially compatible (defect for T10).
  - PSR(0) and DSR are printed with `.3g` (R37; the first round's 4 decimals showed 1e-10 as 0.0000).
  - Recording a holdout use is the CLI's job: a direct `run_wfo_daily(..., WfoConfig(final_holdout=True))` call (scripts, notebooks) passes the guard and is **not** recorded in `HOLDOUT_USES.md`. The intraday engine `step3j_wfo.py` has no holdout guard (Phase 2).
- Known limitations / missing data:
  - **V comes from the legacy (biased) trial results**: their exit-date Sharpe ratios carry the defects T1–T4 removed (same-close fills, stale cross-listed prints, dropped positions, exit-date booking), so their dispersion (sd 0.99 annualised around a mean of +1.18) — and SR₀ ≈ 2.5 annualised — is larger than corrected re-runs of the same configurations would give. Re-running ~100 historical configurations under the corrected engine is out of scope; the DSR here is therefore very conservative. PSR(0) does not depend on the trials.
  - N is a lower bound (see "Not counted"); the owner may know of trials not saved to disk.
  - `bias_test.py` and the `run_*.sh` scripts call the CLI without `--end`: on the real panel they now stop with the holdout message until `--end 2023-12-31` is added (moved to T10).
  - Pre-existing, unchanged: with cfg.end after the panel's last date, `make_windows` builds windows up to cfg.end, so the MTM span carries zero days past the data (lower Sharpe; no data read).
  - Only the CLI prints N and the DSR; the downstream scripts (bootstrap, dashboard, stress, factor attribution) do not yet (T10 / T11).
  - Concurrent CLI runs append in completion order, so their N depends on the order.
